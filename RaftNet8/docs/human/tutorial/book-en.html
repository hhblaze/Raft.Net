Chapter 01

What you are building

Raft.Net8 is an embedded consensus library. You run a host process for each replica, give it a transport and a deterministic application, and submit commands to its elected leader. The library orders and replicates those commands. Your application decides what the bytes mean and stores the resulting business state.

The supported implementation is RaftNet8/src/Raft, targeting net8.0 only. Its assembly is Raft.Net8 and its namespace is Raft. DBreeze is pinned to 1.142.2026.1016-beta. That suffix is the upstream package version, not a setting to remove. The old Framework/Standard projects and legacy-source/ are historical material with different contracts.

We will build a small replicated key/value service. Three processes will keep separate durable copies. A successful put means that a voter quorum has persisted the command and the leader has applied it. We will then restart a process, create a snapshot, and repeat the exercise with entirely volatile storage.

The library is not your public client API

The embedded core has no public service endpoint. The optional Raft.Cluster.Server and Raft.Cluster.Client libraries now provide named streams, HTTP(S), leader discovery and retries; see the following client chapters. This book also teaches the lower-level embedded API. Hosts still provide their application access policy.

How to use this book

  1. Run the existing human demo if you want to see the behavior immediately.
  2. Build the companion examples/TutorialNode and start three terminals.
  3. Read application, write and read semantics before adapting the code.
  4. Use the disk, memory, limits and recovery chapters before deploying persistent data.

All commands below start in the repository's RaftNet8/ directory unless stated otherwise. The two editions have identical chapter anchors; the language switch preserves your current chapter. Everything needed to read this HTML is embedded. The adjacent C# project is needed only to run the examples.

Chapter 02

RaftClusterNodes and external RaftClients

The optional Raft.Cluster.Server, Raft.Cluster.Client and Raft.Cluster.Protocol DLLs add named message streams over the consensus core. One cluster has one leader across all entities and an arbitrary server count. External clients never vote, campaign or become learners.

Each node has separate peer TCP and application HTTP(S) endpoints. The SDK verifies GroupId, bootstraps from any reachable seed, discovers the leader and retries on the current route. It refreshes the advertised client endpoint directory every second by default and raises TopologyChanged; KnownEndpoints is an immutable view. This is periodic discovery rather than instantaneous server push.

Start a node in C#

The compiled helper below starts one node. Invoke it in three processes with n1/n2/n3 and identical bootstrap; each receives its own directory. Retain the returned host with await using and keep the process alive. These disk/large-message timers are a sample profile, not new core defaults.

Connect the application

The first append atomically creates a missing Standard entity. Explicitly call CreateEntityAsync(name, EntityMode.HighSpeedCache) for cache mode. Modes cannot change and counters never reset. Each entity receives its own increasing message IDs during atomic application, independently of technical Raft log indices.

For Hot Add, the host calls server.AddNodeAsync(peer, clientEndpoint, operationId). It first replicates the advertised client address, then starts the journaled membership operation. The address appears in topology when the node acquires a role. Users of low-level node.AddNodeAsync must also call RegisterClientEndpointAsync. Continue redirected administrative calls on the new leader with the same ID. Embedding RaftClusterServer around an existing node requires MessageLedger and ConfigureMessageLimits before node construction.

Discovery needs a reachable anchor

If every address a disconnected client knew has disappeared, discovery cannot invent the new addresses. Keep a seed or stable DNS/bootstrap origin reachable, or refresh the client's initial configuration.

Separate terminals

The sample uses loopback peer ports6101.., client ports7101.., group movies and three original voters. Supply identical --peer-base-port/--client-base-port values to change ports. Start n4/n5 with the original voters, then type add n4/add n5 on the leader. Both sides target net8.0; HTTP v1 remains supported and the new ledger has explicit cluster-v2 identity.

Unauthenticated HTTP is a trusted-network choice. ConfigureHttpServer configures Kestrel/HTTPS; native tokens and AccessTokenProvider enforce request permissions, with Authorize retained as an extra host hook. Configure peer mTLS separately; discovery distributes addresses, never private keys. The new dashboard/security chapters give the full procedure.

Chapter 03

Retained history, cache and application cursors

ModeDisk stateAfter a long disconnect
StandardAll payloads, metadata, counter and request resultsEvery message strictly after afterMessageId
HighSpeedCacheLatest payload, counter and request results; bounded RAM value cacheOnly the available latest value above the cursor; IDs may have gaps

Standard has no automatic TTL or history removal. Old cache commands also remain in the technical log until snapshot/compaction; SnapshotIntervalEntries defaults to0/manual. Configure an interval or schedule snapshots for technical-log reclamation. Deleted DBreeze blocks may remain physically allocated/reusable. Raft compaction removes technical log entries, not the application message ledger. Snapshots include Standard history, cache latest values, counters, request results and endpoint metadata. A clean replacement node can therefore serve old Standard messages after snapshot installation, even if the original technical entries were compacted.

Payload subscriptions receive (entityName, messageId, data); ID-only subscriptions receive (entityName, messageId). ID-only reads neither load payloads from DBreeze nor send them over the network. The SDK fetches bounded batches and invokes callbacks serially per subscription. True advances its current in-process cursor. False or an exception retries the same message, so an unacknowledged ID may repeat. Successfully acknowledged positions increase. A cache retry retains the fetched batch while the process lives; after restart the overwritten value may no longer exist.

A callback follows quorum commit and leader application. It does not wait for every follower or external consumer. Publication does not wait for subscribers. A stable requestId plus identical bytes makes uncertain publication retries idempotent; different content returns request_conflict. Cancellation of a wait does not undo a possible commit.

Your application owns the durable cursor

Commit business effects/data and messageId in the same local database transaction, then return true. On restart read that ID and supply afterMessageId. The cluster stores no ClientId, consumer offsets or subscription ACK commands.

If the local transaction commits and the process crashes before true, restart from the saved cursor. Updating effects and cursor separately risks skipped work or duplicate effects. Delivery is at least once; use a local outbox and an idempotent receiver for external effects. Publisher request deduplication is separate from subscription positions.

Request results have no TTL, including in cache mode. Cache mode bounds retained payloads, not all on-disk metadata growth. The value cache defaults to32MiB and128entries, warming a fitting set of latest values after restart and loading other values on demand. Entity deletion and message-ID reset are not provided.

Chapter 04

Large files, Stream APIs and resource bounds

One payload may contain at most 16,000,000 bytes, leaving envelope headroom within the core's16MiB command ceiling. Split a movie into messages in a Standard entity. After every complete chunk has a successful publication result, publish a manifest in another entity containing the chunk entity, ordered IDs, total length and SHA-256.

The SDK accepts ReadOnlyMemory<byte>, a Stream with declared length, or a Stream read to EOF. One bounded logical message is buffered per operation for repeatable transport retries; a known length avoids a growable MemoryStream. The caller owns the input stream and must keep memory payloads unchanged until completion. Encryption/compression belong to the application; transformed bytes must also fit the payload ceiling.

CopyMessageToAsync copies one message into the destination through a bounded transfer buffer. A broken mid-body download leaves partial bytes; discard or rewind/truncate that chunk before retrying. The example creates a new destination and never overwrites an existing file. There is no built-in file service, decoding or orphan-chunk cleanup.

Buffer limits do not describe total RSS: serialization, Raft, transactions, HTTP and GC add overhead. Higher concurrency multiplies live buffers. Each node stores its own Standard history. Repeatable experiments

Chapter 06

RaftClient tokens and administrator security

HTTP and plain TCP remain supported for trusted networks. New dashboard/management listeners default to loopback. The secure profile requires HTTPS for client/admin APIs and peer mTLS; invalid configuration stops startup. The host supplies certificates, keys and CA roots; Raft never distributes them.

Connect an application

The provider runs before discovery and every HTTP retry. One client serves many entities through a shared connection pool. The token is not a ClientId and does not replace a subscriber's saved cursor. Store it in the application's secret store, never URLs or logs.

Issue a scoped token

Issue a token using a stable operationId. The cluster stores its ID, SHA256 hash of a random256-bit secret, expiry and permissions; the secret is returned once. A retry after a lost response returns the same metadata with Secret=null. Revoke and replace that unusable token. BootstrapAsync creates the first root credential locally using a host secret; its default expiry is30 days. Rotate it before expiry and preserve another administrative access path.

Permissions are checked before request bodies, after ReadIndex for reads and at log application for writes. A revocation ordered before a command blocks it; an earlier ordered command may finish. Admission time is recorded by the leader for deterministic replay, so synchronize host clocks. A timeout remains uncertain. Retrying a publication uses the same requestId, data and credential; its admission timestamp may change.

Browser accounts

Dashboard accounts use ASP.NET Identity: Viewer reads assigned clusters, Operator manages membership/entities, Admin manages accounts and tokens. Even Admin needs CanReadPayload for preview. Create the first account with bootstrap-admin while the dashboard is stopped. Secure mode requires TOTP for Admin/Operator; preserve single-use recovery codes. HttpOnly/SameSite cookies and CSRF protect the browser session; lockout and rate limits restrict guessing. Sensitive actions require authentication within5 minutes.

Without quorum

Only a specially trusted dashboard mTLS certificate may read node-local resources/status without ReadIndex. It grants neither payload nor mutations/token issuance. Without it only cached observations remain. Losing the last administrative secret never enables a quorum bypass.

Contents ↑Entity policies and durable operations →
Chapter 07

Entity policies and durable operations

Policies and publications share Raft order. Quota validation and messageId advancement are atomic, so concurrent clients cannot overshoot. Standard counts all retained payload bytes; HighSpeedCache counts the latest value. Lowering a quota never deletes data. Pausing blocks new publications while reads continue. Entity mode is immutable; this version has no deletion, counter reset or memory-only stream.

The admin SDK uses separate management endpoints. Add/Remove, snapshot and transfer have durable intentions and observable results. One control operation occupies the shared lane at a time. The library never starts the new process: an operator first starts JoiningNode with the original bootstrap membership, then Add verifies capabilities and introduces a learner. Business publications continue during catch-up. A new leader resumes the committed intention.

Chapter 09

The cluster, the log and a quorum

A voter participates in elections and commitment. A learner receives history and is excluded from quorum counting; it cannot campaign. The leader coordinates replication; followers receive its entries. A term is an election epoch, and a log index is an entry's position. A committed entry is part of the agreed history. An applied entry has also reached the local application.

VotersQuorumUnavailable voters toleratedMeaning
110Useful for learning; no replica fault tolerance.
220Two copies but both are required for progress.
321A common small deployment.
532More failure tolerance and more replication work.

For a fixed active configuration, quorum is voterCount / 2 + 1 using integer division. Count the local node only when it is a voter. Learners and merely provisioned KnownPeers do not increase or satisfy that quorum. During membership changes the active configuration comes from the latest configuration entry in the log, including an uncommitted entry; do not calculate operational membership from an old startup file.

Explore lost voters

Fixed-membership arithmetic only: progress also requires connectivity, an eligible leader and healthy storage.

When a three-voter group loses two voters, safe writes and fresh quorum-confirmed reads stop. A remaining process may still display old data. Calling that process a leader does not manufacture a majority. More replicas improve failure tolerance; they do not divide one group's writes into independent shards.

The implementation persists term/vote before dependent responses and log entries before replication acknowledgment. An elected leader appends a no-op, and its current-term commitment rule protects earlier history. You use these guarantees through the node API; your application must still make its own effects replay-safe.

Contents ↑Implement deterministic business state →
Chapter 14

Implement deterministic business state

Raft replicates command bytes, not arbitrary mutations made directly to your database. Generate request IDs, timestamps and other decisions before submitting, include them in the command, and make every replica interpret that command identically. A schema/version field makes unsupported commands visible instead of silently changing meaning.

The gateway validates business input and encoded byte length before calling ProposeAsync. The library also enforces its own byte bound, but cannot validate your JSON schema. A malformed command discovered only during application has already entered the consensus history; the sample halts on that execution failure rather than pretending the caller merely supplied invalid input.

The application stores values under 1.ToIndex(key) and original request results under 2.ToIndex(requestId) in one physical business table, book/data. The helper has a separate book/checkpoint table for its checked (index, term) checkpoint. Both tables participate in the same short DBreeze transaction. The helper reserves them before dependent reads, commits once, and only then publishes its applied frontier.

Do not call Commit inside the handler. Do not open a transaction on a captured live engine, await, call a remote service, use the clock/randomness, or mutate a live cache from this replay handler. Snapshot creation replays it against a separate generation. A direct write to a business table outside committed application bypasses replication and breaks replica equivalence.

Built-in helpers automatically skip business effects for no-op/configuration entries but advance the checkpoint through them. If you implement IStateMachine yourself, inspect entry.IsNoOp and still advance LastApplied. A durable application should implement ICheckpointStateMachine and report the index/term matching its actual durable effects. IBatchStateMachine amortizes application transactions without changing log order.

State-dependent business rejection is a result

For insufficient funds, an ID collision or another valid business rejection, persist a deterministic result and advance the checkpoint. Throwing from Apply is a fail-stop signal, not a convenient way to return a normal business error. The sample keeps the first ID result and reports collisions after application.

Chapter 15

Write, retry and interpret the result

ProposalResult contains the newly committed entry's Index and Term. It is not an application return value. The example reads its own durable request-result row after success to distinguish a first execution, a duplicate and a conflicting reuse of the ID. In a general service, persist the business result and expose a request-result query through the leader's read path.

OutcomeMeaningCaller response
SuccessDurable voter quorum and local leader application completed.Use the result; followers may still lag.
NotLeaderExceptionThis node cannot accept the leader operation; LeaderId may be null.Refresh routing; submit the same request identity and intent.
Cancellation / caller timeoutWaiting stopped; a command may still be committed or later applied.Query/retry using the same request ID and payload.

The embedded ProposeAsync API does not supply client deduplication; the optional message service does. The sample's durable result record, business effect and checkpoint share one transaction. Retries therefore preserve the first business effect even if the original reply was lost. They still consume log entries and application work; deduplication is not a transport optimization.

Keep a request ID stable across retries and bind it to the same payload. Generate a new ID only for a new logical operation. The sample retains request results forever, so its database can grow even if the key count is constant. A production design needs bounded sessions/retention with a clearly defined retry horizon; deleting old results while clients can retry allows duplicate effects.

External effects need another protocol

A committed callback does not make email, payments or HTTP calls exactly-once. Persist an outbox record with the business effect, then use an external delivery worker and an idempotent receiver. Snapshot replay must not resend external actions.

Do not mutate or return pooled command memory while ProposeAsync is still using it. The node makes an owned copy after admission; keeping the input stable until completion is the simple safe calling rule. Request cancellation does not retract a command from the durable log.

Chapter 16

Read current data safely

ReadIndex is a fence, not a returned database snapshot. The leader confirms a fresh voter-quorum context, requires current-term commitment, captures a committed index, and waits for local application through that index. Then read the same leader's concurrency-safe application. The read may include later applied writes, which is acceptable for a current read.

Do not obtain ReadIndex on n1 and then read n2's local database. Do not cache the fence and reuse it for unrelated future requests. Status.Role == Leader, a recent heartbeat, or LastApplied == CommitIndex is not a fresh quorum confirmation. During a partition, a stale former leader can still expose old local data.

APIPurposeCost / boundary

The generation application's Read method protects the active engine during generation switches. Return materialized values or DTOs from its callback, not lazy DBreeze rows, enumerators, nested handles or engine references. A ReadIndex fence does not turn arbitrary multi-table application reads into a transactional snapshot; coordinate complex read consistency in your application.

There are no lease reads or automatic follower-to-leader forwarding. The host chooses the public query endpoint and handles leadership changes. A stale-read API can be useful, but should say so explicitly to its consumers.

V4 is one primary table, not one file

What is not durable

Open sockets, pending caller tasks, read contexts, volatile leader role, in-flight RPCs and the bounded log cache are runtime state. The log cache accelerates access to durable entries; its 8 MiB default is not the entire database and is not a durability mode. After restart the runtime reconstructs participation and catches up from persisted state.

No automatic log retention without snapshots

With SnapshotIntervalEntries=0 and no manual snapshots, the log keeps growing. With snapshots, old log entries may be removed, but business data and deduplication rows remain in the application image. Snapshot retention is not application-data retention.

In-memory mode and its real limits

The modern implementation does have a memory log factory. It runs the DBreeze storage engine with Storage = MEMORY. For a completely volatile lab, the example also uses a separate memory DBreeze engine for business effects and checkpoint, and leaves SnapshotDirectory null.

Wait for Leader, put a value, then quit. Run the same command again and read after the new election: the value and request-result rows are gone. This mode does not persist Raft or business data to a database folder; TCP still uses sockets, the CLR still allocates memory, and the operating system can page process memory. It is not a promise that bytes never reach the machine's swap or diagnostics storage.

Chapter 19

Snapshots, compaction and catch-up

A snapshot represents application state through a committed, applied (index, term) plus the configuration at that fence. Once a complete image is durable and published, the log can compact older history. A far-behind follower then receives an image and continues with later entries instead of requiring every removed command.

Configure an absolute, exclusive SnapshotDirectory and an ISnapshotStateMachine. DBreezeGenerationStateMachine supplies that implementation for a separate absolute application root. Set SnapshotIntervalEntries above zero for automatic builds; zero is manual-only. The tutorial uses manual builds so the data lifecycle is visible.

  1. A build pins a committed/applied fence and replays the deterministic handler into an independent generation, seeded from the prior image when available.
  2. The generation is closed and archived. Images have SHA-256 digests; metadata/descriptors are checked.
  3. The durable image is published and compaction retains the configured log tail.
  4. Transfers use bounded CRC-checked chunks, durable incoming progress and resumable offsets. Installation uses an intent and an atomic generation pointer so restart can finish it.

This approach avoids assuming DBreeze provides a database-wide MVCC snapshot. The price is replay CPU, extra transactions, image I/O and temporary disk space. Plan for the live app, build/replay or prepared generations, archives and retained log at the same time. MaxSnapshotBytes and MaxSnapshotUnpackedBytes bound one archive/extraction; they do not cap total directory usage.

Cancellation stops the caller's wait; it need not cancel an already running snapshot build. Concurrent retention, reception or another build may make manual creation report busy. Published/transfer/prepared images can be pinned beyond the ordinary retention count. Never delete pinned files, modify generation pointers, or truncate the log manually.

A snapshot is not a disaster-recovery reset button

An image alone is not a supported force-new-cluster API. Keep the log, business generation and snapshot repository in a coherent backup, with the same identities and application format. A compacted log cannot rebuild a fresh app without its compatible image.

Chapter 20

Hot Add/Remove without restarting replicas

In wire3 + UnifiedTableV4, existing processes accept entirely new IDs and routes without restart. InitialPeers is the canonical bootstrap directory (every original voter/learner needs a live descriptor, checked when creating a fresh store); KnownPeers remains bootstrap configuration. Read the current immutable view through node.PeerDirectory and node.Status.Membership. A discovered route confers no vote: roles come from the latest logged configuration, including uncommitted entries.

One Add covers the whole workflow

  1. Your host or operator starts the new process: same GroupId and original Members/Learners/InitialPeers, its own stable ID and endpoint, JoiningNode=true. Do not insert self into the original Learners or voters. Until the logged learner arrives, Role=Removed means outside the configuration; actual retirement has an IsRetired directory tombstone. The flag confers no vote and can remain set on restart: recovered membership controls the role.
  2. Call AddNodeAsync(peer, operationId, token) on the current leader. Its intent and registration commit by quorum before subsequent actions.
  3. The library distributes routes, logs the learner, waits for acknowledged MatchIndex catch-up, logs promotion and records completion.
  4. Ordinary commands and ReadIndex continue during catch-up. An unavailable or slow learner keeps the operation active until success or explicit cancellation.

Idempotence and redirection

Persist the non-empty Guid and complete request at the caller. The same ID/content joins the original operation; different content with that ID throws MembershipOperationConflictException. Another ID while the lane is occupied gets MembershipChangeInProgressException with the active ID. Add/Remove wait for a terminal Completed, Cancelled or Failed status. Inspect Stage and Error: returning a status does not itself mean success.

A timeout or cancelled token stops waiting only. It does not cancel an accepted operation. After NotLeaderException, update client routing and retry the same ID/content on the new leader, or call GetMembershipOperationAsync. That is a fresh quorum read on the leader; null means it has no committed intent/result for that ID. Local Status is diagnostic.

Removing the leader

RemoveNodeAsync(id, operationId, token) first persists intent. To remove the current leader, it selects a reachable voter by highest acknowledged MatchIndex, then ordinal ID. Transfer briefly stops new admission on the old leader. The successor commits a current-term entry and continues the saved removal. The old caller commonly receives NotLeaderException and must contact the successor with the same ID. A confirmed transfer failure produces Failed; the old leader is never forcibly removed. Losing the caller connection is not evidence of transfer failure.

Explicit Add cancellation

CancelMembershipOperationAsync journals cancellation. Before the final promotion configuration is appended, it removes the learner created by this operation, commits registry cleanup, then ends Cancelled and releases the lane. Committed entries are never rolled back. Once the voter configuration is appended, cancellation throws MembershipCancellationTooLateException with its current Status; query again when needed. Repeating an already completed cancellation returns Cancelled. For completed/failed operations the too-late exception includes the terminal Status. Remove/Promote are not cancellable Add operations.

The lane belongs to the whole operation

Elections, restarts and caller deadlines do not release it. In wire3, legacy AddLearnerAsync/PromoteToVoterAsync/RemoveNodeAsync use the coordinator too. Standalone leadership transfer cannot bypass an active operation. A reachable quorum, MinimumVoters, one pending configuration and a committed current-term entry remain mandatory.

Try 3 → 5 in terminals

Start the original n1/n2/n3 as in the startup chapter. If changing --data or --base-port, pass matching values to all five processes and adjust Add endpoints. Wait for each terminal result; existing terminals/PIDs remain unchanged. To remove the leader itself, repeat the command in its successor's console with the original GUID.

Transfer leadership for maintenance

Transfer requires an eligible voter. The current leader stops accepting new proposals, reads and configuration changes, catches up the target, sends TimeoutNow and waits to observe the requested new leader. The operation succeeds on that observation or aborts within the election-timeout mechanism. An arbitrary learner cannot become the target until promoted.

Handle LeadershipTransferInProgressException as a transient routing condition. Cancellation does not retract a transfer request already sent. A successful transfer is not proof that your public load balancer has switched; route clients and issue a fresh ReadIndex on the new leader before stopping the old host.

For planned rolling maintenance, transfer away from the host you will stop, keep a voter quorum running, verify catch-up after restart, and only then move to another voter. The library does not choose a global maintenance schedule or move application-owned resources for you.

Automatic byte budgets

The small/bulk windows collect proposals outside the consensus owner. With modern wire2/3 and CoalesceCommitNotifications=true, an idle caught-up follower may learn the new commit index on the next data packet or scheduled heartbeat. A client deadline is independent of RpcTimeout and election timers. Choose it for admission + durable replication + leader application, not just one network trip. Do not treat a timeout as proof of rejection. The sample's 15-second console deadline is an exercise setting, not a library constant.

Use bounded concurrency and measure real work

The recipe caps concurrently executing submissions at 64. It still requires your command producer, input bodies and public server queues to be bounded. Launching millions of tasks with Task.WhenAll merely moves the unbounded memory outside the Raft admission semaphore. Successful calls include leader application, so a slow deterministic handler directly limits useful throughput.

  1. Keep one DBreeze engine per physical directory and short synchronous transactions. Never await inside a transaction.
  2. Declare all write tables at helper construction. For custom read–modify–write transactions, reserve the full write set before dependent reads.
  3. Use ordered/prefixed keys and bounded ranges. Avoid full-table scans in application and maintenance hot paths.
  4. Separate command payload, application-batch, durable-group and replication limits; increasing one does not increase them all.
  5. Measure with the intended voter count, payload size, durable application work, disk and network. Record p50/p99 and allocation as well as commands per second.

The runtime has a dedicated storage thread per adapter and an application thread per started node, alongside async network/timer work and DBreeze activity. Hosting many groups in one process therefore has a thread/resource cost. The pure consensus reducer itself performs no I/O; that does not make synchronous storage flushes free.

Chapter 27

Secure the peer network and your client API

Plain TcpRaftTransport is appropriate only on a trusted lab/network. Group and peer IDs in an RPC are routing identifiers; they are not cryptographic authentication. A production host should restrict the network and use mutual TLS with a certificate-to-Raft-ID policy.

The certificate is caller-owned and must contain the private key. The shown policy keeps platform chain, name and revocation checks and additionally pins each allowed identity to a trusted SHA-256 certificate hash. Configure those hashes out of band. The default TLS TargetHost is the peer's Raft ID, so its certificate SAN/name must validate for that ID, not merely for an unrelated IP address.

A private PKI may supply an explicit validation callback, but it must actually validate that PKI/name policy. Returning true for every certificate defeats authentication. Plan certificate rollover, trust changes and revocation availability across the entire group. TLS handshake work is subject to the transport's RPC timeout, so very slow validation can affect availability.

Peer mTLS does not authenticate your business clients. Add authorization, rate/body limits, request deadlines and request-ID policy to the public HTTP/gRPC/service layer. Command payloads and database files can contain business secrets; the library's CRCs and SHA-256 image digests detect corruption, not confidentiality or a malicious replica.

Failure model

This is crash/recovery Raft for non-Byzantine nodes. It does not tolerate a member intentionally lying, arbitrary operator edits to tables, or storage that acknowledges flushes without preserving the required data.

Move from a lab to a service

  1. Use separate failure domains and disks for voters. Three processes on one laptop demonstrate protocol behavior, not machine-failure tolerance.
  2. Give each replica stable identity and persistent storage. Keep node ID/data together across service restarts and avoid simultaneously active clones.
  3. Provide reachable peer routes, firewall/TLS policy and compatible bounds on every member.
  4. Define a public leader-aware request layer, bounded admission, business validation and durable request results.
  5. Gate readiness on recovered healthy state and successful leader/quorum read or write behavior, not merely process startup.
  6. Connect Completion to a supervisor, close transport before storage, and practice restarts/restore before taking live traffic.

The companion binds only loopback and accepts local stdin commands. It deliberately has no production admin HTTP endpoint. Its --base-port, --data, --single and --memory switches are sample CLI features, not RaftOptions or library command-line flags.

For container/service hosting, use persistent volumes with storage semantics you have verified. Do not let every restarted container receive a fresh data directory while retaining its old voting identity. Separate liveness from readiness: a process waiting for quorum can be alive without being able to serve strong reads/writes. Repeatedly restarting it does not fix missing peers.

Run stable application/command formats on all replicas, including snapshot replay. A rollout that changes the interpretation of already committed commands can diverge business state even when the Raft log is correct. The library does not version/migrate your application handler for you.

Chapter 30

Back up, recover and replace replicas

Normal process restart

Stop/dispose cleanly when possible, keep the same node/group identity and paths, and start through CreateAsync. Recovery validates checksummed records, the durable frontier and application checkpoint, resolves pending image installation, and replays/catches up as required. A clean shutdown is useful, but the disk-backed path is also designed for abrupt process failure under the storage assumptions.

Backup

The simplest operational baseline is a stopped, coherent backup of the node's log database, application root and snapshot repository. Close every engine before a plain directory copy. Preserve descriptors, generation pointers and identity. An ordinary live copy of a few table files is not automatically consistent. DBreeze backup facilities need a coordinated design with the separate application/image roots.

One lost replica while quorum is healthy

Preserve failed files for investigation. Prefer supported replacement through provisioned new identity → learner → catch-up → promotion → removal, keeping a quorum available. Do not erase a current voter and reboot it empty under the same identity. Restoring a stopped replica requires a backup/history compatible with the still-running group.

Whole-group disaster

Restore enough original identities from coherent backups containing the required committed history, then validate ReadIndex/write/read/catch-up before reopening clients. Backup age limits which acknowledged writes can be recovered. There is no safe-quorum-reset/force-new-cluster API that infers missing history from a stale single node.

Checksums detect; they do not heal every loss

A CRC mismatch or app/log checkpoint mismatch is a reason to stop and investigate/restore, not to edit the record until startup passes. Durability still relies on the OS/device honoring flushes. Software fault tests do not prove physical power-loss behavior.

Fresh v4 is a separate mode

The copy command below is only for legacy v2→v3; it does not produce v4. Retain old data and use fresh directories for a new wire3 group.

The API is RaftStorageMigration.CopyV2ToV3(source, destination, options). Use a non-existent destination outside the source. The tool verifies/copies/converts the database folder and seals the result; an incomplete target must not start. It copies application tables inside that DB folder unchanged, but not sibling application or snapshot roots. Copy those separately while stopped. Reparse/outside-table layouts are rejected by this copy method.

Keep the original node/group and recovered membership. Verify the migration manifest/frontiers, start a quorum, exercise reads/writes/catch-up/snapshots and another restart, then reopen clients. Once the new cluster accepts writes, the old folders are stale and are not a safe rollback.

Larger wire2 defaults require compatible peers

For a rolling binary upgrade with older wire2 nodes, explicitly set MaxReplicationBytes=262144 (or that cluster's older MaxAppendBytes) on every new node and retain it through the rollout. Raise limits only when all receivers are compatible; coordinate stop/configure/restart when send and receive limits cannot be changed independently. V2/v3 storage layouts can use the same wire2; no data conversion is needed merely for the frame-limit setting.

Wire1 requires pre-vote off, no snapshots and its old byte budget; modern ReadIndex, transfer and membership controls are unavailable. Compatibility fixtures do not make historical pre-.NET-8 databases automatically migratable. Use the runbook's separate v1→v2 procedure only for the supported raft8-v1 format.

Operational scope: crash/recovery within a non-Byzantine deployment, ordinarily one region.
