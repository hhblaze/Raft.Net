Глава 01

Какое приложение мы создаём

Raft.Net8 — встраиваемая библиотека распределённого консенсуса. Вы запускаете отдельный процесс для каждой реплики, передаёте ему транспорт и детерминированное приложение, а затем отправляете команды избранному лидеру. Библиотека упорядочивает и реплицирует команды. Ваш код определяет смысл байтов и сохраняет получившееся прикладное состояние.

Поддерживаемая реализация находится в RaftNet8/src/Raft и работает только с net8.0. Имя сборки — Raft.Net8, пространство имён — Raft. Версия DBreeze закреплена: 1.142.2026.1016-beta. Суффикс beta является частью опубликованной версии зависимости. Старые проекты Framework/Standard и legacy-source/ сохранены как исторические материалы с другими контрактами.

Мы построим небольшое реплицируемое хранилище ключей и значений. Три процесса будут держать независимые дисковые копии. Успешный put означает, что кворум голосующих узлов сохранил команду, а лидер применил её к приложению. Затем мы перезапустим процесс, создадим снимок и повторим опыт с полностью энергозависимым хранением в RAM.

Публичный API для клиентов создаёт ваше приложение

Ядро не открывает публичный сервисный endpoint. Дополнительные библиотеки Raft.Cluster.Server и Raft.Cluster.Client теперь предоставляют именованные потоки, HTTP(S), обнаружение лидера и повторы: см. следующие главы о клиентах. Остальные главы также обучают низкоуровневому embedded API. Политику доступа задаёт хост.

Как читать книгу

  1. Запустите существующую демонстрацию, если хотите сразу увидеть выборы и репликацию.
  2. Соберите соседний проект examples/TutorialNode и откройте три терминала.
  3. Перед изменением примеров разберитесь в контракте приложения, записи и чтения.
  4. Перед работой с постоянными данными прочитайте главы о диске, памяти, лимитах и восстановлении.

Если не указано иное, все команды выполняются из каталога репозитория RaftNet8/. У обеих языковых версий одинаковые адреса глав: переключение языка сохраняет выбранную главу. Для чтения этой HTML-книги не нужны сервер, интернет и установка зависимостей. Соседний проект C# нужен только для запуска примеров.

Глава 02

RaftClusterNodes и внешние RaftClients

Дополнительные DLL Raft.Cluster.Server, Raft.Cluster.Client и Raft.Cluster.Protocol предоставляют готовый слой именованных сообщений поверх ядра. Один кластер имеет одного лидера для всех entities; число узлов не зафиксировано. Внешний клиент не является voter или learner и не участвует в выборах.

У каждого узла два разных endpoint: peer TCP для консенсуса и HTTP(S) для приложений. Клиент получает seed-адреса, проверяет GroupId, обнаруживает лидера и повторяет запрос на актуальном маршруте. Сервер возвращает справочник client endpoints; SDK обновляет его в фоне, по умолчанию каждую секунду, и вызывает TopologyChanged. Сохраняется неизменяемое представление KnownEndpoints. Это периодическое обновление, а не мгновенный server push.

Запуск узла на C#

Следующий скомпилированный helper запускает один узел. Вызовите его в трёх процессах с n1/n2/n3 и одинаковым bootstrap; каждый получает собственную директорию. Сохраните возвращённый объект через await using и держите процесс работающим. Профиль таймеров здесь выбран для диска и больших сообщений; это не новые defaults ядра.

Подключение приложения

Новая Standard entity автоматически создаётся первой записью. Для HighSpeedCache сначала вызовите CreateEntityAsync(name, EntityMode.HighSpeedCache). Режим существующей entity не меняется, счётчик не сбрасывается. MessageId назначается при атомарном применении на сервере, независимо для каждой entity; это не индекс журнала Raft.

При добавлении узла хост вызывает server.AddNodeAsync(peer, clientEndpoint, operationId). Сначала журналируется клиентский адрес, затем выполняется Hot Add. Адрес рекламируется клиентам после появления роли узла в конфигурации. Если используется низкоуровневый node.AddNodeAsync, дополнительно зарегистрируйте клиентский адрес через RegisterClientEndpointAsync. Смена лидера требует продолжить административную операцию на новом лидере с тем же ID. Для подключения уже работающего узла используйте RaftClusterServer с MessageLedger и заранее настройте ConfigureMessageLimits.

У seed есть физическая граница

Если за время отключения исчезли все известные клиенту адреса, новый адрес неоткуда узнать. Сохраните хотя бы один доступный seed, стабильный DNS/bootstrap адрес либо обновите начальную конфигурацию клиента.

Попробовать в отдельных терминалах

Пример использует peer порты 6101.. и client порты 7101.., loopback, group movies и исходные три voters. Для иных портов задайте одинаковые --peer-base-port/--client-base-port всем процессам. Узлы n4/n5 запускаются с прежним исходным составом, а затем добавляются командой add n4/add n5 на лидере. Обе стороны используют net8.0; прикладной HTTP v1 и ledger cluster-v1 не являются legacy API.

HTTP без авторизации предназначен для доверенной сети. ConfigureHttpServer настраивает Kestrel/HTTPS, Authorize проверяет права каждого запроса. Клиент принимает собственный HttpClient для токенов/mTLS и сохраняет обычную проверку сертификата сервера. Peer mTLS настраивается отдельно; справочник распространяет публичные адреса, а не ключи.

История, cache и курсор приложения

РежимЧто хранится на дискеПосле долгого отключения
StandardВся история payload, metadata, счётчик и результаты запросовВсе сообщения строго после переданного afterMessageId
HighSpeedCacheПоследний payload, счётчик, результаты запросов; значение кэшируется в ограниченной RAMТолько доступное последнее значение с ID больше курсора; возможны пропуски

Standard не имеет автоматического TTL или удаления истории. Старые cache команды также остаются в техническом журнале до snapshot/compaction; SnapshotIntervalEntries по умолчанию равен0, поэтому снимки запускаются вручную либо настраиваются явно. Удалённые блоки DBreeze могут оставаться физически выделенными для повторного использования. Компактизация Raft удаляет технические записи, но не сообщения прикладного ledger. Снимок содержит историю Standard, последние cache значения, счётчики, результаты публикаций и справочник адресов. Поэтому совершенно чистая нода после установки снимка может отдавать старые Standard сообщения, даже если исходный технический журнал уже удалён.

Подписка с данными вызывает (entityName, messageId, data), ID-only — (entityName, messageId). ID-only не читает payload из DBreeze и не передаёт его по сети. SDK получает ограниченные пакеты, затем вызывает обработчик последовательно. True продвигает только текущий курсор процесса. False или исключение повторяют то же сообщение; значит, неподтверждённый ID может повториться. После true следующие ID возрастают. У cache во время retry удерживается полученный пакет; после перезапуска старое значение уже может отсутствовать.

Обработчик вызывается для данных, подтверждённых кворумом и применённых лидером. Не требуется применения всеми репликами или обработки всеми внешними клиентами. Публикация не ждёт подписчиков. Повтор сетевого запроса безопасен с тем же requestId и теми же байтами. Другое содержимое с тем же ID возвращает request_conflict; отмена ожидания не отменяет возможный commit.

Курсор сохраняет ваше приложение

Запишите business effects/данные и messageId одной транзакцией вашей локальной БД. Сначала Commit, затем return true. После перезапуска прочитайте этот ID и передайте afterMessageId. В кластере нет ClientId, таблиц consumer offsets или Raft-команд для ACK подписок.

Если локальная транзакция успела завершиться, а процесс упал до true, после рестарта приложение продолжает с сохранённого ID. Если курсор и эффекты обновлялись отдельно, возможны пропуски либо повторы эффектов. Доставка at least once; для внешних действий используйте локальный outbox и идемпотентного получателя. Запросы с requestId дедуплицируются сервером отдельно от курсора подписки.

Результаты requestId сохраняются без TTL, в том числе в cache. Поэтому cache ограничивает число хранимых payload, но не весь рост дисковых metadata. RAM-кэш последних значений ограничен 32 MiB и 128 элементами по умолчанию; после рестарта заполняется доступным набором последних значений. Доступные тела читаются по запросу. Удаления entity и сброса messageId в этой версии нет.

Глава 04

Большие файлы, Stream и границы ресурсов

Максимальное тело одного сообщения — 16 000 000 байт. Это десятичные MB; служебный envelope помещается в предел 16 MiB ядра. Большой фильм не является одной командой: приложение разбивает его на части, публикует каждую часть в Standard entity и только после успешных результатов публикует manifest в другой entity. Manifest содержит имя entity, упорядоченные IDs, общую длину и SHA-256.

SDK принимает ReadOnlyMemory<byte>, Stream с указанной длиной и Stream до EOF. Буферизуется не более одного логического сообщения на операцию для повторяемой отправки; при известной длине нет растущего MemoryStream. Исходный Stream остаётся собственностью вызывающего. Данные memory-перегрузки должны оставаться неизменными до завершения. Сжатие и шифрование выполняет приложение; кластер не интерпретирует байты. Следите, чтобы размер уже преобразованного тела тоже укладывался в лимит.

CopyMessageToAsync передаёт тело одного сообщения в целевой Stream через ограниченный буфер. Если связь оборвалась в середине, в целевом Stream остаётся часть данных: приложение должно откатить позицию/длину перед повтором этой части. Пример создаёт новый файл и никогда не перезаписывает существующий. Встроенного сервиса файлов, декодирования или автоматической очистки частей нет.

Ограничения буферов не равны полному RSS процесса: сериализация, Raft, транзакции, HTTP и GC имеют собственные накладные расходы. Увеличение concurrency умножает возможные живые буферы. Данные каждого Standard потока копируются на все узлы. Снимки generation создают дополнительную БД и образ; для истории 80 GB стандартного лимита image 64 GiB недостаточно. Задайте достаточные MaxSnapshotBytes/MaxSnapshotUnpackedBytes, измерьте свободное место и время catch-up.

Повторяемые эксперименты

stress-file проверяет свободное место с запасом для исходника, результата, журналов и БД реплик. Он не создаёт снимок 80 GB. Успешный небольшой сценарий и тесты сообщения 16 MB не означают, что 80 GB уже проверены. Клиентские замеры включают HTTP и сохранение всей истории; их нельзя напрямую сравнивать с прежними benchmark ядра с другой бизнес-транзакцией.

Глава 05

Кластер, журнал и кворум

Голосующий узел, или voter, участвует в выборах и подтверждении истории. Ученик, или learner, получает журнал, исключён из подсчёта кворума и не начинает выборы. Лидер координирует репликацию; последователи получают его записи. Term — эпоха выборов, index — положение записи в журнале. Committed означает, что запись стала частью согласованной истории. Applied означает, что локальное приложение уже выполнило эту запись.

ГолосующихКворумДопустимо недоступныхПрактический смысл
110Удобно для обучения; отказоустойчивости между репликами нет.
220Две копии, но для продолжения работы нужны обе.
321Обычный небольшой кластер.
532Выше устойчивость к отказам и больше работы по репликации.

Для фиксированного активного состава кворум равен voterCount / 2 + 1 при целочисленном делении. Сам узел учитывается только тогда, когда он голосующий. Ученики и просто перечисленные в KnownPeers адресаты кворум не увеличивают и не заменяют. При изменении состава активная конфигурация определяется последней записью конфигурации в журнале, в том числе ещё не подтверждённой. Старый файл запуска не является источником текущего кворума.

Попробуйте потерю узлов

Только арифметика фиксированного состава: доступность также требует связи, избираемого лидера и исправного хранилища.

Если в группе из трёх голосующих недоступны двое, безопасная запись и свежее чтение с подтверждением кворума останавливаются. Оставшийся процесс может показывать старое значение. Название Leader в устаревшем представлении не создаёт большинство. Дополнительные реплики повышают устойчивость к отказам, но не делят поток записей одной группы на независимые шарды.

Реализация сохраняет term/vote до зависимого ответа, а записи журнала — до подтверждения репликации. После избрания лидер добавляет no-op; правило подтверждения записей своего term защищает предыдущую историю. Через API узла вы используете эти гарантии, но повторное выполнение прикладных эффектов всё равно должно быть безопасным.

Подготовка .NET 8 и сборка

Установите SDK .NET 8. Файл global.json выбирает семейство 8.0.400 с переходом на последний доступный feature band внутри .NET 8. Поэтому dotnet --version из каталога RaftNet8/ должен показывать 8.0.x даже при установленном более новом SDK. Исходники используют C# 12, nullable-типы и предупреждения как ошибки.

Соседний учебный проект намеренно не включён в основное решение. Соберите его один раз до открытия нескольких терминалов: тогда процессы не будут одновременно пересобирать один каталог результатов.

Подключение проекта библиотеки

Этот относительный путь правильный именно для соседнего учебного проекта. В своём приложении скорректируйте путь к src/Raft/Raft.csproj и задайте net8.0. Централизованные версии зависимостей и lock-файлы обеспечивают нужную версию DBreeze. Номер сборки в исходниках сам по себе не означает, что соответствующий пакет уже опубликован в NuGet.

Версия зависимости и формат данных — разные вопросы

Восстановление более нового пакета базы не мигрирует журнал Raft, схему приложения или сетевой протокол. В примерах используется закреплённая в репозитории зависимость и явно выбранный формат v3.

Наблюдение за готовой демонстрацией

Самый быстрый опыт — существующее решение HumanTest. Его три узла работают в одном процессе, но общаются по настоящему TCP через loopback и используют разные дисковые базы и каталоги снимков.

Сначала посмотрите status и определите фактического лидера, затем изолируйте именно его. Указанный ниже n1 — пример, а не обещанный победитель выборов.

Демонстрация сама направляет set/get известному лидеру; в вашем сервисе такую маршрутизацию нужно реализовать. Команда get выполняет ReadIndex перед запросом к приложению. Во время выборов или изменения состава административная команда может сообщить о незавершённом переходе. Дождитесь стабильного состояния и повторяйте операции по одной.

Детерминированная прикладная модель

Raft реплицирует байты команд, а не произвольные изменения, выполненные напрямую в вашей базе. Создавайте ID запроса, время и другие внешние решения до отправки, включайте их в команду и одинаково интерпретируйте на всех репликах. Поле версии позволяет явно обнаруживать неподдерживаемые команды вместо незаметного изменения смысла старой истории.

Входной шлюз проверяет бизнес-поля и размер закодированных байтов до вызова ProposeAsync. Библиотека дополнительно проверяет свой размерный лимит, но не знает вашей JSON-схемы. Если недопустимая команда обнаружена только при применении, она уже попала в согласованную историю. Пример останавливается при такой ошибке выполнения, а не выдаёт её за обычную ошибку входных данных.

Приложение сохраняет значения по ключам 1.ToIndex(key), а первые результаты запросов — по 2.ToIndex(requestId) в одной физической бизнес-таблице book/data. Вспомогательный класс использует отдельную таблицу book/checkpoint для проверяемой пары (index, term). Обе таблицы изменяются одной короткой транзакцией DBreeze. Класс резервирует их до зависимых чтений, делает один Commit и лишь затем публикует применённый индекс.

Внутри обработчика нельзя вызывать Commit, открывать транзакцию на захваченном живом engine, выполнять await, обращаться к внешним сервисам, часам или случайным данным, изменять живой кэш. При построении снимка этот обработчик выполняется повторно в отдельном поколении базы. Запись в бизнес-таблицу в обход применения подтверждённой команды нарушает репликацию и равенство состояний.

Готовые классы автоматически пропускают бизнес-эффекты no-op и записей конфигурации, но продвигают через них checkpoint. В собственной реализации IStateMachine проверяйте entry.IsNoOp и всё равно обновляйте LastApplied. Постоянное приложение должно реализовать ICheckpointStateMachine и сообщать пару индекс/term, соответствующую реальным дисковым эффектам. IBatchStateMachine объединяет применение в транзакции, сохраняя порядок журнала.

Обычный бизнес-отказ — это результат

Недостаточный баланс, занятый ID и другой допустимый бизнес-отказ оформляйте как детерминированный сохранённый результат с продвижением checkpoint. Исключение из Apply — сигнал остановки узла, а не способ вернуть обычную бизнес-ошибку. Пример сохраняет первый результат ID и обнаруживает конфликт после применения.

Встроенной дедупликации клиентов в библиотеке нет. В примере строка первого результата, бизнес-эффект и checkpoint сохраняются одной транзакцией. Поэтому повтор не повторяет первый бизнес-эффект, даже если ответ потерялся. Однако повторы всё ещё создают записи журнала и работу приложения: это не оптимизация транспорта.

ID запроса должен оставаться тем же при повторах и соответствовать одному содержимому. Новый ID создаётся для новой логической операции. Учебное приложение хранит результаты запросов бессрочно, поэтому база растёт даже при постоянном числе ключей. Для рабочей системы нужны ограниченные сессии/срок хранения и понятный горизонт повторов. Удаление старого результата при ещё допустимом повторе позволяет повторный эффект.

Внешним эффектам нужен отдельный протокол

Подтверждённый callback не делает письмо, платёж или HTTP-вызов exactly-once. Сохраните outbox вместе с бизнес-эффектом, затем доставляйте его отдельным worker с идемпотентным получателем. Повтор приложения при построении снимка не должен повторно отправлять внешние действия.

Не меняйте входные байты и не возвращайте арендованный буфер в пул, пока ProposeAsync ещё использует его. Узел создаёт собственную копию после admission; простое безопасное правило — сохранять входную память неизменной до завершения вызова. Отмена запроса не изымает команду из постоянного журнала.

Как безопасно прочитать актуальные данные

ReadIndex — барьер, а не готовый снимок базы. Лидер подтверждает свежий контекст кворумом, требует подтверждения записи текущего term, фиксирует committed index и ждёт локального применения как минимум до него. После этого читайте потокобезопасное приложение того же лидера. Результат может включать и более поздние уже применённые записи — это допустимо для актуального чтения.

Нельзя получить ReadIndex на n1, а затем прочитать локальную базу n2. Нельзя кэшировать барьер для произвольных будущих запросов. Проверка Status.Role == Leader, недавний heartbeat и равенство LastApplied == CommitIndex не являются свежим подтверждением кворума. При сетевом разрыве бывший лидер может продолжать показывать старое локальное значение.

V4: одна основная таблица, а не один файл

Таблица raft8/v4 хранит изменяемое состояние консенсуса в упорядоченных пространствах ключей: 1.ToIndex(metadataKey), 2.ToIndex(logIndex), 3.ToIndex(configurationIndex), а также 4 для служебного индекса и 5 для результатов. Hard state и постоянные границы объединены проверяемым RF4M manifest. В старых таблицах метаданных также сохраняются небольшие защитные записи, чтобы несовместимый reader отказался от открытия. Системные и rollback-файлы DBreeze остаются. Слово unified не означает, что для резервной копии достаточно одного файла таблицы.

V2 использует raft8/v2/meta, raft8/v2/log и raft8/v2/config. У записей v2/v3 есть проверки целостности; это обнаружение повреждения, а не шифрование и не защита от злонамеренного участника. Учётные 21 байт на запись относятся к бюджетам памяти/передачи. Проверяемая дисковая запись добавляет 37 байт до собственных расходов DBreeze на ключи, индексы и транзакционный журнал. Нельзя оценивать объём диска только по полезным данным.

Что не сохраняется постоянно

Открытые сокеты, ожидающие задачи клиентов, контексты чтения, текущая роль лидера, незавершённые RPC и ограниченный кэш журнала — состояние runtime. Кэш ускоряет доступ к постоянным записям. Его лимит 8 МиБ по умолчанию не равен размеру базы и не выбирает режим долговечности. После рестарта runtime восстанавливает участие и догоняет историю по постоянным данным.

Без снимков нет автоматического ограничения журнала

При SnapshotIntervalEntries=0 и без ручных снимков журнал продолжает расти. Снимки позволяют удалять старые записи журнала, но бизнес-данные и строки дедупликации остаются внутри состояния приложения и образа. Хранение снимков не является политикой удаления прикладных данных.

Режим в памяти и его реальные ограничения

В современной реализации есть фабрика журнала в памяти. Она запускает DBreeze с Storage = MEMORY. Для полностью энергозависимого опыта пример также использует отдельный memory-engine для бизнес-эффектов и checkpoint и оставляет SnapshotDirectory равным null.

Дождитесь Leader, запишите значение и завершите процесс. Запустите ту же команду ещё раз и прочитайте после новых выборов: значение и сохранённые результаты запросов исчезли. Этот режим не сохраняет данные Raft и приложения в каталог базы; TCP всё ещё использует сокеты, CLR выделяет память, а ОС может выгружать страницы процесса. Это не обещание, что байты никогда не попадут в swap или диагностический дамп машины.

Если узел забывает term, vote и журнал, а затем возвращается под прежней голосующей идентичностью, нарушаются предпосылки стабильного хранения Raft и может нарушиться безопасность. Нельзя перезапускать потерявший память voter в живой рабочий кластер как прежнюю реплику. Используйте дисковых голосующих и поддерживаемую процедуру замены состава. Каждый запуск полностью RAM-опыта считайте новой одноразовой группой.

Изменение LogCacheBytes не переводит хранилище в RAM. Встроенная реализация поколений и снимков использует диск. Memory-режим соседнего проекта намеренно не поддерживает снимки. При этом прикладная RAM-база продолжает расти с новыми значениями и ID запросов до завершения процесса.

Снимки, compaction и догоняющая репликация

Снимок представляет прикладное состояние до подтверждённой и применённой пары (index, term) и конфигурацию на этой границе. После надёжной публикации полного образа старый префикс журнала можно удалить. Сильно отставший последователь получает образ и продолжает с более поздних записей вместо запроса всех уже удалённых команд.

Нужны абсолютный эксклюзивный SnapshotDirectory и реализация ISnapshotStateMachine. Класс DBreezeGenerationStateMachine предоставляет её для отдельного абсолютного корня приложения. Положительный SnapshotIntervalEntries включает автоматическое построение; ноль оставляет только ручное. В учебном примере снимки ручные, чтобы жизненный цикл данных был виден.

  1. Построение закрепляет committed/applied-границу и повторяет детерминированный обработчик в независимом поколении, при наличии начиная с предыдущего образа.
  2. Поколение закрывается и архивируется. Для образа вычисляется SHA-256; метаданные и дескрипторы проверяются.
  3. Постоянный образ публикуется, а compaction сохраняет настроенный хвост журнала.
  4. Передача идёт ограниченными блоками с CRC, постоянным прогрессом приёма и возобновляемыми offset. Intent установки и атомарный указатель поколения позволяют завершить переход после рестарта.

Такой путь не предполагает наличия у DBreeze общего MVCC-снимка базы. Цена — CPU для replay, дополнительные транзакции, работа с архивами и временное место. Планируйте одновременное размещение живого приложения, replay/build или подготовленного поколения, архивов и оставшегося журнала. MaxSnapshotBytes и MaxSnapshotUnpackedBytes ограничивают отдельный архив/распаковку, но не весь объём каталогов.

Отмена прекращает ожидание вызывающего, но не обязательно уже начатое построение. Во время retention, приёма или другой сборки ручной вызов может сообщить busy. Текущий, передаваемый или подготовленный образ может быть закреплён сверх обычного числа хранимых снимков. Не удаляйте закреплённые файлы, не редактируйте указатели поколений и не обрезайте журнал вручную.

Снимок не является кнопкой сброса аварийного кластера

Один образ не является поддерживаемым API force-new-cluster. Сохраняйте согласованную резервную копию журнала, поколения приложения и репозитория снимков с прежними идентичностями и форматом приложения. Сокращённый журнал не восстановит новое приложение без совместимого образа.

Hot Add/Remove без рестарта реплик

В режиме wire3 + UnifiedTableV4 существующие процессы принимают новые ID и маршруты без перезапуска. InitialPeers задаёт общий начальный справочник (для каждого исходного voter/learner нужен действующий дескриптор; новая база проверяет это), KnownPeers остаётся bootstrap-настройкой. Текущее неизменяемое представление — node.PeerDirectory и node.Status.Membership. Полученный адрес не даёт права голоса: роли определяет последняя конфигурация в журнале, включая неподтверждённую.

Один Add — вся процедура

  1. Приложение или оператор запускает новый процесс: тот же GroupId, исходные Members/Learners/InitialPeers, собственный стабильный ID и endpoint, JoiningNode=true. Не добавляйте себя вручную в исходные Learners или voters. До записи learner локальный Role=Removed означает нахождение вне состава; реальное удаление отмечается IsRetired в справочнике. Флаг не даёт права голоса и может оставаться при рестарте: восстановленный журнал определяет роль.
  2. На текущем лидере вызовите AddNodeAsync(peer, operationId, token). Намерение и регистрация подтверждаются кворумом до последующих действий.
  3. Библиотека распространяет маршруты, журналирует learner, ждёт подтверждённого MatchIndex, журналирует повышение и завершение.
  4. Обычные команды и ReadIndex продолжают работать при догонянии. Недоступный или медленный learner оставляет операцию активной до успеха либо явной отмены.

Идемпотентность и перенаправление

Сохраните непустой Guid и полное содержимое запроса у вызывающего. Тот же ID и та же цель возвращают прежнюю операцию; другой запрос с этим ID вызывает MembershipOperationConflictException. Другой ID при занятом слоте получает MembershipChangeInProgressException с ID активной операции. Add/Remove ожидают конечный статус Completed, Cancelled или Failed. Проверяйте Stage и Error: возврат статуса сам по себе не означает успех.

Таймаут и отмена token прекращают только ожидание. Они не отменяют принятую операцию. После NotLeaderException обновите клиентский маршрут и повторите тот же ID/содержимое на новом лидере либо вызовите GetMembershipOperationAsync. Это свежий кворумный запрос к лидеру; null означает, что у него нет подтверждённого намерения или результата с этим ID. Локальный Status служит диагностикой.

Удаление лидера

RemoveNodeAsync(id, operationId, token) сначала сохраняет намерение. Для удаления текущего лидера выбирается доступный voter с наибольшим подтверждённым MatchIndex; равенство разрешается порядком ID. Передача на короткое время останавливает новый приём на старом лидере. Преемник подтверждает запись своего term и продолжает сохранённое удаление. Старый вызывающий обычно получает NotLeaderException и должен обратиться с тем же ID к преемнику. При подтверждённом отказе передачи фиксируется Failed; принудительного самоудаления нет. Обрыв связи с клиентом не доказывает отказ.

Явная отмена Add

CancelMembershipOperationAsync подтверждает запрос отмены через журнал. Пока финальная конфигурация повышения не добавлена, библиотека удаляет созданный learner, подтверждает очистку регистрации и лишь затем завершает Cancelled и освобождает слот. Подтверждённые записи не откатываются. Если конфигурация voter уже добавлена, возвращается MembershipCancellationTooLateException с текущим Status; при необходимости запросите его заново. Повтор уже выполненной отмены возвращает Cancelled. Для завершённой или неуспешной операции исключение «слишком поздно» содержит её конечный Status. Remove/Promote не являются отменяемым Add.

Слот принадлежит всей операции

Смена лидера, рестарт или истечение срока ожидания не освобождают слот. Старые AddLearnerAsync/PromoteToVoterAsync/RemoveNodeAsync в wire3 тоже используют координатор. Отдельная передача лидерства не обходит активную операцию. Доступный кворум, MinimumVoters, одна неподтверждённая конфигурация и запись текущего term остаются обязательными.

Проверка 3 → 5 в терминалах

Запустите исходные n1/n2/n3 по главе запуска. При изменении --data или --base-port передайте те же параметры всем пяти процессам и скорректируйте порты в Add. После каждого шага ждите конечного результата; существующие терминалы/PID остаются теми же. Для удаления самого лидера повторите команду в консоли нового лидера с прежним GUID.

Хранение, доверие и пределы изменения состава

Что переживает рестарт

В единственной основной физической таблице raft8/v4 префиксы 1.ToIndex(...) хранят метаданные/RF4M, 2 — журнал, 3 — индекс конфигураций, 4 — разреженный индекс служебных операций, 5 — результаты по generation/operationId. Активная операция и справочник материализованы как ограниченное служебное состояние. Обычная запись не сканирует всю административную историю. Результаты читаются по ключу с диска; весь список не загружается в RAM.

Служебные записи доходят до прикладного checkpoint без бизнес-эффекта; собственный обработчик должен пропускать entry.IsNoOp и всё равно продвигать index/term. DBreeze-помощники делают это автоматически. V4-снимок связывает приложение, справочник, активную операцию и поток результатов на одной границе (index, term). При установке поколение истории переключается атомарно с метаданными журнала после подготовки приложения. При старте незавершённый intent доводится до конца.

Отставшие маршруты и доверие

Перед обычным RPC транспорт ограниченно обменивается справочником при подключении или изменении revision. Отставший узел может узнать нового лидера через доверенного peer, даже если прежние контакты удалены. Это лишь маршрутизация: подсказки не меняют voters, term, checkpoint и состояние операции. mTLS сначала проверяет цепочку/имя и привязку сертификата к ID. Корни доверия, политика авторизации и закрытые ключи принадлежат хосту и через справочник не распространяются. Plain TCP разрешён для доверенной сети.

Граница совместимости

Wire3 требует явно выбранный UnifiedTableV4. Смешанные wire1/wire2/wire3 и открытие старого каталога как v4 отклоняются. Конвертера v2/v3→v4 сейчас нет: режим рассчитан на новые кластеры, поскольку развёрнутых старых кластеров у проекта нет. Старые codecs/golden fixtures и v1/v2/v3 режимы остаются для совместимости. Старый путь с заранее известными ID не получает hot Add автоматически.

Безопасность важнее числа работающих процессов

Добавление второго voter меняет кворум с 1 на 2; две копии не дают отказоустойчивость одной потери. Удаление не исправляет потерянный кворум, не обходит MinimumVoters и не запускает новый OS-процесс. Совместимые command format/ApplicationId, сеть, PKI и запас диска остаются ответственностью хоста.

Передача лидерства перед обслуживанием

Целью передачи должен быть допустимый голосующий. Текущий лидер прекращает принимать новые предложения, чтения и изменения состава, догоняет цель, отправляет TimeoutNow и ждёт, пока увидит её новым лидером. Успех означает такое наблюдение; незавершённая передача прерывается механизмом election timeout. Произвольный ученик не может стать целью до повышения.

Считайте LeadershipTransferInProgressException временным состоянием маршрутизации. Отмена ожидания не отзывает уже отправленную передачу. Успех не означает, что ваш публичный балансировщик уже переключился: обновите клиентский маршрут и выполните свежий ReadIndex на новом лидере до остановки старого хоста.

При плановом последовательном обслуживании сначала передайте лидерство с останавливаемого узла, сохраняйте работающий кворум, после рестарта проверьте догоняющую репликацию и лишь затем обслуживайте следующего voter. Библиотека не составляет глобальное расписание обслуживания и не переносит ресурсы вашего приложения.

С настройками по умолчанию предел пакета/локальной группы равен 1 051 264 Б — 1 МиБ + 2688 Б. Предел тела кадра — 1 052 288 Б; TCP-префикс длины добавляет ещё 4 байта. Кадр чуть больше 1 МиБ может арендовать bucket ArrayPool на 2 МиБ. Длина кадра не равна точному объёму managed heap.

Например, команда после кодирования размером 16 КиБ учитывается как 16 405 байт. Стандартный пакет применения вмещает 15 таких записей, а локальная группа или пакет wire2/3 — 64 с учётом счётного предела. Для полных закодированных команд по 64 КиБ эти бюджеты вмещают соответственно 3 и 16 записей. Размер JSON включает метаданные и экранирование: значение на 16 КиБ не обязательно превращается в команду на 16 КиБ.

Малое и bulk-окно собирают команды вне владельца консенсуса. Явная ненулевая bulk-задержка остаётся переопределением даже при нулевой малой. Измеряйте обмен между задержкой и числом транзакций: последовательный поток по одной команде не показывает поведение 64 параллельных вызывающих.

Задержка уведомления commit — осознанный компромисс

При современном wire2/3 и CoalesceCommitNotifications=true догнавший idle-последователь узнаёт новый commit index со следующим пакетом данных или плановым heartbeat. Его применение может отстать на этот логический heartbeat плюс I/O/сеть/очередь владельца. Кворумное сохранение и применение лидером всё равно предшествуют успеху клиента. Значение false возвращает немедленную попытку отправки, но существующий flight тоже может задерживать адресата. Для свежего чтения нужен ReadIndex лидера.

Дедлайн клиента независим от RpcTimeout и выборов. Он должен учитывать admission, постоянную репликацию и применение лидером, а не один сетевой обмен. Таймаут не доказывает отказ команды. 15 секунд ожидания в учебной консоли — настройка упражнения, не константа библиотеки.

Ограниченный параллелизм и полезная нагрузка

Рецепт ограничивает одновременно исполняемые отправки числом 64. Производитель команд, тела входящих запросов и очереди публичного сервиса тоже должны быть ограничены. Миллионы задач в Task.WhenAll просто переносят неограниченную память за semaphore admission узла. Успешный вызов включает применение лидером, поэтому медленный детерминированный обработчик напрямую ограничивает полезную скорость.

  1. Держите один DBreeze engine на физический каталог и используйте короткие синхронные транзакции. Никакого await внутри транзакции.
  2. Перечисляйте все записываемые таблицы при создании helper. В своих read–modify–write транзакциях резервируйте полный write set до зависимых чтений.
  3. Применяйте упорядоченные составные ключи, префиксы и ограниченные диапазоны. Избегайте полного сканирования таблиц на горячем пути и в обслуживании.
  4. Разделяйте размер команды, пакет применения, локальную постоянную группу и сетевой пакет: изменение одного не изменяет автоматически остальные.
  5. Измеряйте нужное число голосующих, реальные размеры команд, постоянную работу приложения, диск и сеть. Фиксируйте p50/p99 и выделения памяти вместе с командами в секунду.

На каждый storage-адаптер приходится отдельный поток хранения, а на запущенный узел — поток приложения; дополнительно работают асинхронные сеть/таймеры и DBreeze. Поэтому много групп в одном процессе имеют цену по потокам и ресурсам. Чистый reducer консенсуса не выполняет I/O, но синхронный дисковый flush от этого не становится бесплатным.

Отчёт hot membership сравнивает wire3/v4 с предыдущим HEAD, включая полный Add под нагрузкой. Оценивайте скорость, p99 и выделения памяти отдельно: локальный диск/TCP не обещает ёмкость сети разных машин. Ранее выпущенный отчёт R18 с конкурентами относится к версии до hot membership и сохранён как историческое свидетельство.

Защита сети узлов и клиентского API

Обычный TcpRaftTransport подходит для доверенной лабораторной сети. Имена группы и участника внутри RPC — маршрутизация, а не криптографическая аутентификация. В рабочем хосте ограничьте сеть и включите взаимный TLS с привязкой сертификата к идентичности Raft.

Сертификат принадлежит вызывающему и должен содержать закрытый ключ. Показанная политика сохраняет системные проверки цепочки, имени и отзыва и дополнительно сверяет каждый ID с доверенным SHA-256-хэшем сертификата. Хэши доставляются доверенной конфигурацией, а не самим собеседником. TLS TargetHost по умолчанию равен ID участника Raft: SAN/имя сертификата должны подходить этому ID, а не только постороннему IP-адресу.

Для собственной PKI можно передать явный validation callback, но он обязан действительно проверять выбранную цепочку/политику имён. Безусловный true отключает защиту. Согласуйте ротацию, изменение доверия и доступность проверки отзыва на всей группе. TLS-handshake ограничен транспортным RpcTimeout, поэтому медленная валидация тоже влияет на доступность.

Peer mTLS не авторизует ваших бизнес-клиентов. В публичном HTTP/gRPC/сервисном слое нужны собственные права, rate/body limits, дедлайны и правила ID запросов. Команды и файлы базы могут содержать секретные данные. CRC и SHA-256 образов обнаруживают повреждения, но не обеспечивают конфиденциальность и не защищают от злонамеренной реплики.

Модель отказов

Это Raft для crash/recovery незлонамеренных, non-Byzantine узлов. Он не защищает от намеренно лгущего участника, произвольной ручной правки таблиц или накопителя, который подтверждает flush, не сохраняя необходимые данные.

Переход от упражнения к сервису

  1. Разместите голосующих в разных доменах отказа и на разных дисках. Три процесса на ноутбуке показывают протокол, но не отказоустойчивость к потере машины.
  2. Назначьте стабильные идентичности и постоянные каталоги. При рестартах сохраняйте связку ID/данные и исключите одновременно активные клоны.
  3. Обеспечьте доступные маршруты, firewall/TLS и совместимые пределы у всех участников.
  4. Создайте публичный слой маршрутизации к лидеру, ограничение admission, бизнес-валидацию и постоянные результаты запросов.
  5. Определяйте readiness по здоровому восстановленному состоянию и успешному чтению/записи через кворум, а не факту запуска процесса.
  6. Подключите Completion к супервизору, закрывайте транспорт до хранилища и отрепетируйте рестарт/restore до рабочего трафика.

Учебный процесс слушает только loopback и принимает локальный stdin. У него намеренно нет административного production HTTP endpoint. Ключи --base-port, --data, --single и --memory принадлежат этому примеру, а не RaftOptions и не командной строке самой библиотеки.

В контейнерах и службах нужны постоянные тома с проверенными свойствами хранения. Нельзя выдавать каждому новому контейнеру пустую базу, оставляя прежнюю голосующую идентичность. Разделяйте liveness и readiness: процесс без кворума может быть жив, но не способен обслужить сильные чтения/записи. Постоянный рестарт не возвращает отсутствующих участников.

Сохраняйте совместимый формат команд и приложения на всех репликах, включая replay снимков. Изменение смысла ранее подтверждённых команд во время rollout может привести к расхождению бизнес-состояний даже при правильном журнале Raft. Библиотека не версионирует и не мигрирует ваш обработчик автоматически.

Резервные копии, восстановление и замена

Обычный рестарт

По возможности корректно остановитесь, сохраните те же идентичности и каталоги, затем запускайтесь через CreateAsync. Восстановление проверяет записи с контрольными суммами, постоянные границы и checkpoint приложения, завершает незаконченный переход снимка и при необходимости применяет/догоняет историю. Чистая остановка полезна, но дисковый путь рассчитан и на аварийное завершение процесса при выполнении предпосылок хранения.

Резервная копия

Простой эксплуатационный базис — согласованная копия остановленного узла: база журнала, корень приложения и репозиторий снимков. Перед обычным копированием каталогов закройте все engine. Сохраните дескрипторы, указатели поколений и идентичности. Живое копирование нескольких файлов таблиц само по себе не гарантирует согласованности. Средства backup DBreeze требуют общего плана с отдельными корнями приложения/образов.

Одна реплика потеряна, кворум исправен

Сохраните неисправные файлы для разбора. Предпочитайте поддерживаемую замену: заранее известный новый ID → learner → догоняние → повышение → удаление старого, сохраняя кворум. Не стирайте действующего voter и не возвращайте его пустым под прежним ID. Для restore остановленной реплики нужна копия/история, совместимая с оставшейся работающей группой.

Авария всей группы

Восстановите достаточное число прежних идентичностей из согласованных копий, содержащих необходимую подтверждённую историю. Перед открытием клиентского трафика проверьте ReadIndex, запись/чтение и catch-up. Возраст backup ограничивает восстанавливаемые подтверждённые записи. Нет безопасного API quorum-reset/force-new-cluster, которое само выведет утраченную историю из одного старого узла.

Контрольная сумма обнаруживает, но не лечит любую потерю

Ошибка CRC или несовпадение checkpoint приложения/журнала — повод остановиться, исследовать и восстановиться, а не редактировать запись до успешного старта. Долговечность опирается на выполнение flush со стороны ОС/устройства. Программные fault-тесты не доказывают поведение при физическом отключении питания.

Инструмент проверяет, копирует и конвертирует каталог базы, затем завершает его публикацию. Незаконченная цель не должна запускаться. Бизнес-таблицы внутри этого DB-каталога копируются без изменения; соседние корни приложения и снимков не копируются — перенесите их отдельно при остановленных engine. Этот путь отклоняет reparse points и вынесенные наружу таблицы.

Сохраните прежние группу/узел и восстановленный состав. Проверьте manifest и индексы, запустите кворум, выполните чтение/запись, catch-up, снимки и ещё один рестарт, затем откройте трафик. После новых подтверждённых записей прежние каталоги устаревают и не являются безопасным rollback.

Новые крупные пакеты wire2 требуют совместимых узлов

При rolling-обновлении бинарников со старым wire2 задайте каждому новому узлу MaxReplicationBytes=262144 либо старый MaxAppendBytes группы и сохраняйте его до конца rollout. Увеличивайте лимит только после совместимости всех получателей. Если размеры отправки и приёма нельзя менять отдельно, согласуйте stop/configure/restart. V2/v3 диска используют один wire2; одно изменение лимита кадра не требует конвертации данных.

Wire1 требует выключенного pre-vote, отсутствия снимков и старого байтового бюджета; современные ReadIndex, transfer и membership-control недоступны. Совместимые fixtures не делают базы старых pre-.NET-8 проектов автоматически мигрируемыми. Отдельную процедуру v1→v2 из runbook применяйте только к поддерживаемому формату raft8-v1.

Эксплуатационная область — crash/recovery для non-Byzantine развёртывания, обычно в одном регионе. Нет joint consensus, lease reads, автоматической переадресации внутри embedded ядра, гарантий межрегиональной ёмкости и небезопасного сброса кворума. Внешние эффекты требуют прикладного протокола. RAM-хранилище — возможность одноразового опыта, а не замена стабильному хранению.
