Режимы

  • Без пакетов (Unbatched): одна запись на пакет лога, репликации и применения; задержка сбора 0.
  • Пакеты (Batched): до 128 записей / 256 КиБ. Текущая версия собирает пакет с задержкой 1 мс; база забирает уже накопившиеся команды, без настраиваемой задержки.
  • Pipeline: текущая версия, пакеты и окно до 4 сообщений репликации.
  • Без пакетов + pipeline (UnbatchedPipeline): текущая версия, одна запись на пакет, окно 4.
  • База имеет один запрос репликации в полёте; pipeline у неё отсутствует.

Общие условия

  • Concurrency 64, закрытый цикл с насыщением; MaxPending 1024. Это не тест задержки при заданной открытой интенсивности запросов.
  • Одинаковые таймеры: tick 25 мс, heartbeat 1 tick, election [200, 240) ticks (5–6 с), RPC 2 с.
  • Эти таймеры учитывают измеренные дисковые хвосты и очередь без пакетов; их нельзя считать рекомендацией для любого развёртывания.
  • Успех клиента: durable-кворум + применение на лидере. Проверка durable-счётчиков и checkpoint всех реплик выполняется после измерения.

BDN не измеряет p50/p99 отдельного запроса. Среднее время порции делится на 128 и преобразуется в команд/с. Его нельзя читать как пользовательскую задержку. StdDev описывает оставшиеся измерения BDN, а не распределение individual-request latency. Полные доверительные интервалы и предупреждения доступны в исходных BDN-отчётах.

Базовая версия8 неизменённых C#-файлов коммита 8b991bd, изолированных assembly alias; .NET 8 и та же версия DBreeze. V1 / wire 1 имеет более слабый контракт целостности, восстановления и возможностей.
Текущая версияV2 / wire 2, checksummed durable frontier, pure core и новые возможности. Сравнение не означает одинаковых гарантий двух реализаций.
  • Архивные проекты до .NET 8 отличаются API, применением и моментом подтверждения; они не являются эквивалентной базой этого сравнения.
  • Медленный незавершённый диагностический прогон на C-temp исключён. Размещение данных, рост лога, файловая система и планировщик существенно влияют на цифры.
  • Управляемые выделения в latency runner измерены за интервал на весь процесс с репликами; в BDN действует его memory diagnoser. Эти способы измерения не объединяются.
  • Минимальные длительности итераций, фильтрация выбросов и ограничения среды отражены в исходных BDN-отчётах. Это локальные результаты, а не гарантия производительности или hardware power-loss durability.
Оптимизации, проверка и исключённые эксперименты

Сохранённые оптимизации хранилища убирают LRU-сканирование с обычного append/commit, отвечают по известным диапазонам term из кэша с одной ленивой транзакцией при промахе и используют проверенную метаинформацию общего числа байтов при commit до хвоста. Их защищают тесты замены, компактизации, повторного открытия и сравнения DBreeze с моделью.

Эксперимент с обходом worker для неблокирующего чтения кэша прошёл проверки корректности, но показал нестабильную скорость, включая замедление длинного прогона с 5 узлами. Он отменён и не входит в финальные результаты. CPU EventPipe traces использованы только для диагностики: overhead async rundown / ConditionalWeakTable искажает время под профилированием.

Исправленные microbenchmarks выполнили 29 Dry-конфигураций и 6 прогретых wire-конфигураций. Dry подтверждает исполнение, а не производительность. Ранние отчёты генератора с конфликтом aliased return types, исполнившие 0 конфигураций, исключены. Финальные исправления legacy-wire control rejection и offline migration preflight не меняют измеренные proposal/storage/wire 2 пути.
