# Historical experiments and validation

Reference binaries, source archive and hashes were captured before production edits in RaftNet8/.artifacts/winner/reference-runtime/,reference-sources.zip,reference-hashes.json. All temporary measurements/tests for this task live under RaftNet8/.artifacts/winner/. Diagnostics are opt-in and excluded from capacity evidence.

Follower extension at exactly LastIndex+1 now emits Append rather than ReplaceSuffix. Actual term conflicts still use atomic ReplaceSuffix and restore the previous configuration. New red/green AppendFastPathTests and existing durability/core-shape assertions cover both cases. This removes unnecessary suffix/configuration/LRU work; an isolated instrumented run did not establish a throughput gain by itself.

RaftNode proposals use their own bounded channel. A coalesced control-queue notification preserves owner ordering, admission and caller cancellation semantics while interleaved controls no longer fragment already-queued proposals. ProposalChannelTests holds a real durable write, queues64 writes interleaved with63 reads, and proves five bounded batches rather than64 singletons; the reference binary failed that check. Focused runtime/wire/admission tests passed44/44 after dedicated storage worker and pooled frame changes.

RaftStorageAdapter now hosts synchronous DBreeze work on one background thread per adapter, retaining the bounded2-operation channel. It does not set global ThreadPool options. Pool-backed TCP encoding reserves the already-computed frame size once, preserving other segmented IBufferWriter callers and wire bytes.

The first UnifiedTableV3 experiment used nested roots. After the user's explicit ToIndex preference, a rotated3-round isolated probe found prefixed keys slightly faster than nested roots (1.630–1.798ms vs1.760–1.905ms/commit; physical two-table cases5.108–5.632ms). These are diagnostic numbers only. The final unreleased v3 schema uses flat1.ToIndex(metaKey),2.ToIndex(logIndex),3.ToIndex(configIndex) in raft8/v3, with unchanged checked bodies. Nested-prototype sources/runtime are preserved in nested-v3-* artifacts; final readers reject that experimental representation. No deployed/user data used it.

V3 reduces multi-table commit work without removing the atomic frontier, CRC, fsync or common application transaction. Existing constructors still select SeparateTablesV2. V1/v2 readers reject v3 and v3 refuses existing legacy identities/orphan reserved data. CopyV2ToV3 performs a stopped physical copy, bounded raw-record conversion, complete verification, atomic destination sealing and a flushed manifest. Business/checkpoint/snapshot files inside the DB folder are copied; sibling roots require a separate stopped copy. V1-to-v2-to-v3 chains are supported; cancellation leaves an unusable destination. Migration-focused checks passed19/19.
