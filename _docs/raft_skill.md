# Integrate Raft.Net8

Use `RaftNet8/src/Raft/Raft.csproj` and `RaftNet8/Raft.Net8.sln`, targeting **net8.0**. DBreeze is pinned to **1.142.2026.1016-beta**, its actual 1.142 .NET 8 NuGet release. Historical `Raft/`, `RaftStandard/`, deployment packages and excluded `legacy-source/` have different APIs/schemas. Do not infer their contracts from the modern library.

Fresh wire3 stores require a live InitialPeers descriptor for every bootstrap voter and learner. Validate that only at the fresh-store boundary: recovered/current membership can include IDs added after the original InitialPeers. Never compare recovered voters with the original directory to reject them.

Read [the runnable durable example](../RaftNet8/README.md#runnable-durable-example) for construction, [configuration](../RaftNet8/docs/CONFIGURATION.md) for exact defaults/units, and [operations](../RaftNet8/docs/OPERATIONS.md) before changing membership, restoring or upgrading. The complete snapshot-capable application is [SnapshotKeyValueMachine](../RaftNet8/HumanTest/Raft.Demo/SnapshotKeyValueMachine.cs).

For a human introduction use the offline [English/Russian HTML books](../RaftNet8/docs/human/tutorial/index.html) and their compiled `examples/TutorialNode` project. The example supports disk generations/images and a separate all-memory lab; volatile voters do not provide durable restart guarantees.

## Construct and own a node

1. Give each node a stable `NodeId`, common `GroupId`, original voter `Members` and compatible limits. Use distinct directories/endpoints. IDs are1..128 ASCII letters/digits/-/_. For fresh hot-membership groups select `WireVersion=3` and identical canonical `InitialPeers` descriptors. A joiner keeps the same original Members/Learners/InitialPeers and sets `JoiningNode=true`; never inject self into the bootstrap Learners. The flag permits startup outside the configuration, grants no vote, and may stay true on restart. Its initial Role=Removed means outside membership until the logged learner arrives; directory IsRetired identifies actual retirement. Routes do not confer votes.
2. For new wire3 data use `DBreezeLogStorage(path, options, DBreezeLogLayout.UnifiedTableV4)` inside `RaftStorageAdapter`. One primary table has numeric ToIndex prefixes1=metadata/RF4M,2=log,3=config,4=service index,5=terminal results. Defaults retain wire2/v2; v3/wire2 remains compatible. No v2/v3→v4 converter or automatic conversion exists. Use an absolute SnapshotDirectory and a separate absolute DBreezeGenerationStateMachine root for images; DBreezeStateMachine supports a caller-owned engine without images. Do not put business tables under raft8/.
3. Use `TcpRaftTransport(options, localPeerDescriptor, security)` for wire3. A custom transport must implement `IPeerDirectoryTransport` and authenticate/admit trusted IDs before forwarding ordinary RPCs; hints never change voters. `RaftNode.CreateAsync` validates/replays state and completes install intents before elections. Await StartAsync(), then tcp.Start(node.HandleAsync). Local listen requires literal IP; remote DNS resolves asynchronously.
4. Submit to the leader. `NotLeaderException.LeaderId` is a hint and may be null. Observe `node.Completion`: persistence/application execution failure must halt participation, preserving its original exception.
5. Stop transport before node/store, then dispose application and caller-owned engines. After successful creation the node owns the log store; on creation failure the caller still owns it. The adapter owns its wrapped storage. Path-based storage owns its engine; supplied engines are caller-owned unless explicitly transferred. Transports/applications/logger factories/certificates remain caller-owned.

Original `IRaft*` interfaces and four-argument `RaftNode` constructor remain available. New `ITransport`/`IStateMachine`/`IBatchStateMachine` are compatible adapters. Injectable `IClock`/`ITicker`/`IRandom` belong to the runtime, never the pure reducer.

The runtime keeps proposals in a bounded channel separate from controls, with one consensus owner. Each storage adapter owns one background thread for synchronous DBreeze transactions; the started node also owns one application thread, including support for genuine async callbacks. No transaction spans await. Published cached reads complete inline only with nonblocking lock acquisition and no DB I/O; busy/missing reads go through the bounded worker. Count these threads per hosted group when sizing an embedding. The [project DBreeze preference](llm/skill/DBreeze_project_patterns.md) favors one physical table and disjoint `ToIndex` type/index prefixes when appropriate.

## Application, retry and read semantics

`ProposeAsync` succeeds after durable voter-quorum replication and **leader application**, not application on every follower. Commands must be deterministic. Application callbacks receive committed entries in order, including no-op/configuration records: skip their business effects using `entry.IsNoOp`, but advance `(LastApplied, term)` through them. Built-in DBreeze helpers atomically persist effects and CRC index/term checkpoint, reserve all write tables before reads and never await inside a transaction.

The generation handler runs again during independent snapshot replay. Write only its supplied transaction: no captured live engine/cache, external service call, random value or clock. Materialize results within `Read(...)`; never return lazy DBreeze rows/enumerators. A durable app must report the checkpoint corresponding to actual durable effects. A compacted log needs a compatible image/app format; a fresh volatile app cannot rebuild a removed prefix.

Cancellation/timeouts stop waiting and may leave a committed command. Reuse a stable application request ID and deduplicate transactionally with effects/checkpoint. The library does not deduplicate. Keep input memory unchanged until the proposal call finishes. External effects need an application outbox/receiver protocol.

For a linearizable application query, **await leader.ReadIndexAsync(token), then read that leader's concurrency-safe application**. It confirms a fresh quorum context, current-term commit and local applied fence without a new log entry. `ReadBarrierAsync` remains an append/no-op compatibility alternative. Plain local application/status reads are stale-capable. There are no lease reads or automatic follower forwarding.

## Membership, transfer and snapshots

For wire3 use `AddNodeAsync(PeerDescriptor, operationId, token)` for registration→learner→acknowledged catch-up→voter, and `RemoveNodeAsync(nodeId, operationId, token)`. Persist the caller's non-empty Guid and exact request. Same ID/content joins the original operation; conflicting content throws MembershipOperationConflictException. Another ID while occupied gets MembershipChangeInProgressException with the active ID. The lane survives elections/restart and includes an uncommitted local reservation. Ordinary writes/read fences continue while catching up.

Calls wait for terminal MembershipOperationStatus: inspect Stage and Error; Failed/Cancelled is not success. Wait cancellation/timeout does not cancel an admitted operation. After NotLeader, resolve the successor and retry the SAME ID/content or call GetMembershipOperationAsync there (fresh quorum lookup, indexed disk history). Status.Membership / PeerDirectory is an immutable local diagnostic view. An unavailable learner waits until success or explicit CancelMembershipOperationAsync. Explicit cancel before final voter-configuration append commits learner removal and registration retirement before releasing the lane; afterwards it throws MembershipCancellationTooLateException with its current Status (including a terminal result). Repeating an already completed cancellation returns Cancelled. Never erase committed entries to cancel.

Leader removal commits intent, chooses a reachable voter by MatchIndex descending then ordinal ID, and transfers. Its successor commits a current-term entry and resumes removal; the caller follows NotLeader using the same ID. Confirmed transfer failure records Failed without forced self-removal. Legacy membership APIs share the coordinator in wire3; standalone transfer cannot bypass it. AddLearnerAsync requires an already registered descriptor.

The latest logged configuration, including uncommitted entries, defines voters and rolls back with its suffix. The previous configuration and a current-term entry must commit before the next single-server/role change. Count self only if a voter. Wire3 learners may durably answer Vote/PreVote for promotion recovery, but cannot campaign or count themselves. Never edit tables/options to manufacture quorum. Read [the detailed contract](../RaftNet8/docs/HOT-MEMBERSHIP.md) for stages, trust and failure handling.

Legacy wire2 still requires preprovisioned KnownPeers/routes, AddLearner→acknowledged catch-up→Promote and manual transfer for planned removal. Do not apply that restart/provisioning requirement to wire3.

`TransferLeadershipAsync(voterId)` catches up an eligible voter and sends TimeoutNow while stopping new proposals/reads/config changes on the old leader. It succeeds on observing the requested leader or aborts within the election timeout. Require a fresh ReadIndex on the new leader before planned maintenance. Cancellation does not retract a sent transfer request.

`CreateSnapshotAsync` publishes an immutable image and compacts to `SnapshotRetainEntries`; `SnapshotIntervalEntries=0` means manual only. Creation replays to a pinned committed/applied fence in a separate generation, trading extra disk/CPU for consistency without assuming DBreeze MVCC. Chunks use CRC/offsets, images SHA-256; install intent/generation pointer/log publication recover after crashes. Keep log/application/images together in consistent backups; do not edit descriptors or delete pinned images. A bare image is not a force-new-cluster API.

## Security, bounds and diagnostics

Plain TCP is for trusted networks. Pass `TlsRaftTransportSecurity(certificate, authorizePeer, ...)` for mutual TLS 1.2/1.3 with platform chain/name checks and mandatory certificate-to-Raft-ID binding. Default TargetHost is the peer ID, so provision matching SANs. A private-PKI callback must validate that policy, not accept every certificate. UpdatePeerAsync is for provisioned wire1/2 routes only; wire3 routes are owned by the replicated directory. Bounded trusted directory exchange repairs stale routes without changing Core membership, term or commit. mTLS verifies identity before accepting a new-ID exchange; trust roots/private keys/authorization policy remain host-owned.

Defaults: 25 ms ticks, heartbeat 1 tick, elections `[12,24)` ticks, RPC 200 ms. Minimum election >=10× heartbeat; tune all deadlines to measured disk/network/GC tails. Off-owner proposal windows: small2ms, bulk up to8ms while other admitted work awaits quorum/application, single voter1ms; application batches128 entries/256KiB; wire2 packets auto1MiB+2688B (same count cap); commands64KiB; 1024 pending proposals/reads; peer window 4 messages/4 MiB; uncommitted budget 64 MiB; cache 1024 entries/8 MiB. Read the reference for snapshot and validation limits. Backpressure does not bound arbitrary caller-owned waiting tasks.

MaxProposalBatchBytes=null independently permits a bounded local durable group up to min(4×MaxAppendBytes +21×MaxAppendEntries, MaxUncommittedBytes,64MiB), normally1MiB+2688B. MaxAppendEntries still caps its count; application batches retain MaxAppendBytes, wire2 uses MaxReplicationBytes, and wire1 retains MaxAppendBytes. Each command remains a distinct log entry and waits for quorum plus apply. Set MaxProposalBatchBytes=MaxAppendBytes for the earlier local-byte cap; invalid overrides are rejected at construction.

Structured `ILoggerFactory` overloads, Meter and ActivitySource `Raft.Net8` expose role/term/frontiers, peer lag, elections, snapshot progress and proposal/persistence/Commit/apply durations. Histograms use seconds; bytes use `By`. DBreeze Commit timing includes disk flush rather than isolating a syscall. Payloads are excluded. Faulty diagnostics are counted separately and cannot replace a storage/app failure.

Wire3 limits:1024 historical directory IDs including retired/cancelled tombstones (never reuse IDs);4096B service record;900000B service metadata;≤128 history rows/page; frame=max(replication,SnapshotChunkBytes+900000)+1024. Configuration payloads have a separate budget from business MaxCommandBytes and must fit min(270000,MaxAppendBytes−21,ReplicationByteLimit−21). Result history has no TTL and grows on disk; one bounded directory/active view stays in memory. Incoming history stages by image ID; v4 snapshots bind app, directory, active op and streamed results at the same applied index/term. Install atomically switches history with log metadata after application preparation; restart finishes intent. Bounded collection removes obsolete staging, never authoritative results. MEMORY mode also forgets this management state; never rejoin an empty RAM voter under an old live-cluster identity.

## Compatibility and verification

### External message service

For external RaftClients use `Raft.Cluster.Client`; hosts use `Raft.Cluster.Server`, shared contracts `Raft.Cluster.Protocol`. Read [the client contract](../RaftNet8/docs/CLUSTER-CLIENTS.md) when implementing those applications. One Raft group has one leader for all named entities. Client endpoints use a separate HTTP(S) port; they are not peer endpoints or voting identities. SDK seeds/GroupId, authoritative leader discovery and periodic immutable topology refresh handle ordinary rerouting. An offline client still needs a reachable known seed or stable DNS/bootstrap after address turnover.

`AddLogEntryAsync` returns an entity-local messageId after quorum persistence and leader apply. Missing entities auto-create as Standard; explicitly create HighSpeedCache. Standard retains all payloads; cache retains latest payload on disk with a bounded RAM read cache. Both counters and request results survive restart/snapshot. Stable caller request Guids make uncertain publication retries idempotent; different content with the same Guid is rejected. Results have no TTL, so cache metadata still grows. Modes/IDs cannot reset and entities cannot be deleted in this version. The `cluster-v1` application ledger is not a converter for legacy or arbitrary application data.

`SubscribeAsync` receives payload; `SubscribeIdsAsync` avoids payload IO. AfterMessageId is exclusive. Callbacks are serial per subscription, true advances an in-process position, false/exception retries the same message. Cache can skip overwritten IDs. The application commits business effects and durable cursor together locally, then returns true, and supplies that saved cursor after restart. Never invent a persistent ClientId or cluster consumer ACK/offset table. At-least-once delivery remains explicit; external effects need outbox/idempotency.

Maximum payload16,000,000B (envelope fits core16MiB); Stream APIs buffer at most one bounded message per operation, never an80GB file. Transform/compress/encrypt outside the cluster. Use generic chunk entities plus a second manifest entity; `CopyMessageToAsync` retrieves by entity/ID, leaving partial output on a broken download. Limits default to4 requests and8 active subscription buffers per SDK,4 server requests,128 messages/32MiB per response,32MiB/128-entry value cache,4096entities/1024client endpoints. Higher concurrency multiplies buffer memory. Cache old commands also remain in the technical log until snapshot/compaction (SnapshotIntervalEntries defaults to0/manual); latest-only is a logical application retention policy, not secure physical erasure. Standard history remains application state through Raft compaction and snapshots; increase default64GiB image/128GiB unpack limits for large histories and budget replay/install copies.

`RaftClusterNode` owns its store, MessageLedger, peer TCP and client gateway. For an existing node use its MessageLedger and configure message byte limits before construction. `server.AddNodeAsync(peer, clientEndpoint, operationId)` replicates the client origin before the journaled Add; it is advertised when the role appears. Raw node.AddNodeAsync requires explicit origin registration; retry redirected administration on the successor with the same ID. HTTPS/Authorize belong to the host and client credentials to its HttpClient; peer mTLS remains separate. Core wire3/raft8-v4 are unchanged; application HTTPv1 is additive. Run the compiled [client demo](../RaftNet8/HumanTest/Raft.Cluster.Demo/Program.cs), its process verifier and message tests after changes.

Recommend explicit raft8-v4/wire3 for fresh groups; no v2/v3→v4 converter exists. Preserve old data and use fresh directories. V3/wire2 remains a legacy compatibility option. V2/v3 remain supported on wire2; v4 explicitly requires wire3. V1 golden bytes/readers remain explicit but lack integrity frontier/configuration/snapshot support; v1 ReadIndex/transfer calls are rejected (use ReadBarrier). Mixed wire versions fail closed. Use the **whole-group offline copy migration** in [the runbook](../RaftNet8/docs/OPERATIONS.md#upgrade-raft8-v1-to-v2) for v1→v2 and [v2→v3](../RaftNet8/docs/OPERATIONS.md#upgrade-raft8-v2-to-v3) (`CopyV2ToV3` / `Raft.Migrate --v2-to-v3`). Keep group/node identity and copy separate application/snapshot roots while stopped; only files inside the DB folder are copied automatically. Incomplete targets and old readers are rejected. Rolling format conversion is not the validated workflow. Preflight never initializes an unrecognized source. Historical pre-.NET-8 data needs application-specific migration. Full v3 snapshot-log clearing visits retained keys within its namespace in bounded memory. The embedded core provides no joint consensus, leases, Byzantine tolerance or unsafe quorum reset. The optional cluster service supplies external clients and routing; its contract is separate below.

From `RaftNet8/`, run locked restore, Release build/tests and `dotnet run --project HumanTest/Raft.Demo -c Release --no-build -- --scenario`. Replay deterministic faults with `dotnet run --project tools/Raft.Simulator -c Release -- --seed 17 --scenario Mixed --steps 3000 --voters 3`; nightly/large runs use `--seeds 3000 --scenario all --voters 3,5 --parallel 4`. [Benchmarks](../RaftNet8/benchmarks/README.md) distinguish throughput from individual p50/p99 and compare the preserved baseline. When modifying internals, follow [AGENTS.md](../AGENTS.md) and [current specifications/memory](llm/okf/index.md); keep `Raft.Core` pure and execution errors fail-stop.


Published log-cache entries and metadata share a short publication lock separate from the serialized storage/flush lock. Cache-only readers never acquire the storage lock or open a transaction. They may read the previous durable prefix during a later write; future entries still wait for the worker. Publish state/frontier/cache invalidation/new entries together after Commit, and publish poisoning/disposal under the same cache lock. Lock order is storage then cache, never the reverse. Count/byte limits are unchanged.

The bounded proposal channel now has a separate asynchronous collection deadline task. The consensus owner continues processing control/RPC events while commands gather; only that owner drains commands and assigns log indices. The change signal is bounded and carries no command payloads. Leadership/transfer/memory checks still run on the owner before persistence.

BulkProposalBatchDelay is nullable: auto min(4×ProposalBatchDelay, one heartbeat,1second), normally8ms for byte-limited groups while other admitted commands await quorum/application. Count-limited groups keep ProposalBatchDelay (default2ms); single-voter windows cap at1ms. When all admitted work is already queued, the collector uses the small window. Deadlines start at the oldest queued command and never extend on new arrivals. Set BulkProposalBatchDelay=TimeSpan.Zero to disable the intentional bulk wait. Explicit bulk values must fit one heartbeat/one second. This trades bounded intentional collection latency for group amortization; wire/application/count/admission/durability limits remain unchanged.

MaxReplicationBytes is a nullable wire2 byte budget: auto min(4×MaxAppendBytes +21×MaxAppendEntries,MaxInFlightBytes−64,64MiB), normally1MiB+2688B. MaxAppendBytes still bounds application/replay (normally256KiB); local proposal bytes remain independently bounded. Wire1 keeps its original budget. For mixed older wire2 nodes explicitly set MaxReplicationBytes to their MaxAppendBytes (normally262144) through the whole rolling binary upgrade, then coordinate compatible configuration/restarts before raising limits. Older/smaller receivers reject oversized frames; do not assume mixed limits work. No storage/wire-byte conversion is required.

Modern followers may aggregate already-queued plain contiguous fresh Append frames from one voter/current term into one bounded durable write. Each original RPC retains its own reply ID/matched index after persistence; votes/read contexts/configuration/snapshot/term boundaries prevent aggregation. This does not change client quorum-plus-leader-application acknowledgment.

CoalesceCommitNotifications defaults true for wire2 with modern storage. Ordinary idle commit frontiers piggyback on the next data packet or scheduled heartbeat; follower apply can lag by that logical heartbeat plus I/O/network/owner delay. Term/vote/log/commit persistence and quorum-plus-leader-application client completion are unchanged. Read contexts, new configuration, transfer, snapshot progress and retirement retain immediate/control send paths. False restores the prior attempt to send an extra idle commit RPC; a peer with an existing flight can still await later traffic. Wire1/legacy storage retain prior behavior. See specification027 and the majority-only leader-death regressions.
